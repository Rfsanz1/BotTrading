# Laporan Audit Read-Only `/root/BotTrading`

**Tanggal audit:** 2026-09-13  
**Metode:** inspeksi kode aktual, konfigurasi, manifest, Docker/CI, schema Prisma, test, dan artefak readiness. Tidak ada file yang diubah atau commit dibuat.

## Kesimpulan eksekutif

Repository **belum siap untuk paper/testnet/live trading tanpa perbaikan besar**.

Temuan paling serius:

1. **CRITICAL — Endpoint administrasi/RBAC NestJS tidak dilindungi autentikasi.** Siapa pun dapat mengubah role user menjadi `ADMIN`.
2. **CRITICAL — Event fill/order dari exchange hanya disimpan di memory, tidak dipersist ke PostgreSQL.** Saldo, trade, position, dan P&L lokal dapat tertinggal dari exchange setelah order benar-benar terisi.
3. **CRITICAL — Endpoint close position dan update SL/TP hanya mengubah database lokal, tidak mengirim order exit/proteksi ke exchange.**
4. **HIGH — AI provider NestJS seluruhnya mock/hardcoded, tetapi dianggap selalu tersedia.**
5. **HIGH — Risk engine salah memvalidasi SELL/short; semua entry SELL non-exit berpotensi ditolak.**
6. **HIGH — Webhook alert unauthenticated memakai `userId = "system"` yang tidak memenuhi foreign key User UUID; alur webhook aktif kemungkinan gagal di database.**
7. **HIGH — Docker dan healthcheck deployment kontradiktif/tidak dapat dipercaya.**
8. **HIGH — Penyimpanan credential exchange belum aman dan implementasi dekripsi belum ada.**
9. **HIGH — Event handler memakai nama event berbeda dari event yang benar-benar di-emit, sehingga callback tracking tidak pernah berjalan.**
10. **HIGH — Test/CI tidak menjadi gate: test gagal karena dependency, test command di-ignore dengan `|| true`, dan root typecheck gagal.**

# 2. Temuan CRITICAL

## C-01 — RBAC/admin API tidak memiliki authentication guard

**Severity:** CRITICAL  
**File:**

- `apps/api/src/modules/users/users.controller.ts:6-17`
- `apps/api/src/modules/users/users.service.ts:16-31`

Controller user tidak memakai `@UseGuards(JwtAuthGuard)` atau guard role.

```ts
@Post(':id/roles')
async setRoles(@Param('id') id: string, @Body() body: RolesDto) {
  return this.svc.setRoles(id, body.roles);
}
```

Service menerima role apa pun yang valid dari enum, termasuk `ADMIN`.

### Dampak

Unauthenticated attacker dapat:

- Melihat daftar seluruh user melalui `GET /users`.
- Mengambil user berdasarkan ID.
- Menetapkan role `ADMIN` ke akun mana pun.
- Mengubah model otorisasi sistem secara langsung.

### Rekomendasi

- Terapkan global authentication guard.
- Tambahkan `RolesGuard`/permission guard.
- Batasi `POST /users/:id/roles` hanya untuk admin terotorisasi.
- Jangan menerima `userId` arbitrary dari body/path tanpa validasi ownership.

## C-02 — Exchange user-data event tidak dipersist ke database

**Severity:** CRITICAL  
**File:**

- `apps/api/src/modules/trading/trading.service.ts:40-62`
- `apps/api/src/modules/trading/trading-lifecycle.service.ts:83-97`
- `packages/exchange/src/services/exchange-event-router.ts:128-186`

`TradingService.wireExchangeAdapter()` hanya memanggil:

```ts
this.exchangeRouter.handle(payload);
```

`ExchangeEventRouter` menyimpan order, fill, account, dan position di `Map` memory-only:

```ts
private readonly orders = new Map<string, OrderRecord>();
private readonly accounts = new Map<string, Record<string, any>>();
private readonly positions = new Map<string, Record<string, any>>();
```

Tidak ada operasi Prisma pada pemrosesan event fill/order tersebut.

### Dampak

Setelah order Binance terisi:

- `Order.filled` dapat tetap `0`.
- `Trade` tidak tercatat.
- `Position` tidak dibuat/di-update.
- P&L lokal tidak akurat.
- Restart process menghilangkan state event router.
- Sistem dapat mengira posisi masih open/canceled padahal exchange sudah filled.

Ini sangat berbahaya untuk live trading dan reconciliation.

### Rekomendasi

- Satu canonical event consumer harus memetakan exchange event ke order internal berdasarkan `clientOrderId`/`externalOrderId`.
- Persist event secara idempotent ke PostgreSQL.
- Gunakan unique key pada `(exchange, accountId, exchangeOrderId, exchangeTradeId)`.
- Semua fill harus melewati transaction:
  1. insert trade,
  2. update order cumulative fill/status,
  3. update position,
  4. audit event.
- Event router tidak boleh hanya bergantung pada memory.

## C-03 — Close position dan update SL/TP hanya mengubah database lokal

**Severity:** CRITICAL  
**File:**

- `apps/api/src/modules/trading/trading.controller.ts:441-500`
- `apps/api/src/modules/trading/trading.service.ts:1442-1483`
- `packages/exchange/src/services/position.service.ts:242-285`

`closePosition()` memanggil:

```ts
this.tradingService.positionService.closePosition(...)
```

Implementasinya hanya mengubah `Position.status = CLOSED` dan mencatat `realizedPnL`. Tidak ada `orderService.place()`, `cancel()`, atau market exit order ke exchange.

Demikian juga update SL/TP hanya:

```ts
prisma.position.update(...)
```

### Dampak

API dapat mengembalikan “Position closed successfully”, tetapi posisi riil masih terbuka di exchange.

SL/TP yang diperbarui di database tidak menjadi stop order di exchange. Jika aplikasi mati, tidak ada proteksi aktif.

### Rekomendasi

- Close endpoint harus membuat dan mengirim order exit canonical.
- Posisi hanya boleh berstatus `CLOSED` setelah exchange mengonfirmasi fill.
- Update SL/TP harus melakukan amend/cancel-replace order proteksi di exchange.
- Bedakan status lokal:
  - `CLOSE_REQUESTED`
  - `EXIT_SUBMITTED`
  - `EXIT_FILLED`
  - `CLOSED`
- Jangan menerima `closingPrice` dari client sebagai sumber kebenaran; ambil execution price dari exchange.

# 3. Temuan HIGH — trading dan risk

## H-01 — Risk engine salah memvalidasi SELL

**Severity:** HIGH  
**File:** `packages/exchange/src/services/risk-engine.ts:436-440`

```ts
if (!isExit && input.trade.takeProfit <= input.trade.entry && input.trade.action !== 'HOLD') {
  fail('TAKE_PROFIT_VALIDATION', ...)
}
```

Untuk SELL yang valid:

- entry = 100
- stop loss = 105
- take profit = 90

`takeProfit <= entry` selalu benar, sehingga SELL entry ditolak.

### Dampak

- Semua short/SELL entry non-exit berpotensi gagal risk check.
- Sistem menjadi hanya long-biased tanpa dokumentasi eksplisit.
- Hasil AI SELL tidak dapat dieksekusi secara konsisten.

### Rekomendasi

Validasi berdasarkan arah:

- BUY: `stopLoss < entry < takeProfit`
- SELL: `takeProfit < entry < stopLoss`
- EXIT/REDUCE/CLOSE memakai validasi berbeda.

Tambahkan test eksplisit untuk BUY, SELL, REDUCE, CLOSE, dan REVERSAL.

## H-02 — P&L posisi short salah dan partial close tidak mencatat realized P&L

**Severity:** HIGH  
**File:** `apps/api/src/modules/trading/trading.service.ts:805-826`

Saat posisi berlawanan ditutup:

```ts
realizedPnL: (price - position.entryPrice) * quantity
```

Formula ini hanya benar untuk posisi BUY. Untuk posisi SELL, seharusnya:

```ts
(position.entryPrice - price) * quantity
```

Pada partial close, quantity dikurangi tetapi tidak ada realized P&L yang dicatat.

### Dampak

- P&L short dapat terbalik.
- Statistik win/loss salah.
- Risk limit berdasarkan P&L dapat salah.
- Partial exits kehilangan hasil finansial.

### Rekomendasi

Gunakan helper P&L directional yang sama untuk seluruh jalur. Catat realized P&L setiap partial fill dan akumulasikan secara atomik.

## H-03 — Daily loss limit memakai P&L total, bukan P&L harian

**Severity:** HIGH  
**File:**

- `apps/api/src/modules/trading/trading.service.ts:300-320`
- `packages/exchange/src/services/pnl-calculation.service.ts:45-75`

`calculatePnLMetrics()` mengambil seluruh posisi user tanpa filter tanggal. Nilai `realizedPnL` tersebut dipakai sebagai `dailyMetrics.realizedPnL`.

### Dampak

- Loss historis dapat dianggap sebagai loss hari ini.
- Atau loss hari ini tidak terukur dengan benar jika posisi/event belum dipersist.
- Kill switch dan daily loss limit tidak dapat dipercaya.

### Rekomendasi

Implementasikan query harian berbasis `closedAt`/trade timestamp, timezone eksplisit, dan termasuk unrealized loss sesuai kebijakan risk.

## H-04 — Duplicate fill dapat menggandakan quantity trade

**Severity:** HIGH  
**File:** `apps/api/src/modules/trading/trading.service.ts:620-658`

Jika `fillQuantity <= 0`, kode mengambil trade pertama lalu mengubah:

```ts
quantity: newFilled
```

Jika order sebelumnya mempunyai beberapa partial fills, `newFilled` adalah cumulative quantity, bukan quantity delta. Mengubah satu trade lama menjadi cumulative value dapat menggandakan total quantity.

### Dampak

- P&L dan position quantity membengkak.
- Duplicate atau replay event dapat merusak accounting.
- Reconciliation menjadi tidak deterministik.

### Rekomendasi

- Simpan setiap exchange trade/fill dengan `exchangeTradeId` unik.
- Duplicate event harus menjadi no-op.
- Jangan memperbarui quantity fill lama menjadi cumulative quantity.
- Gunakan cumulative fill hanya untuk update `Order.filled`.

## H-09 — Webhook alert aktif tanpa auth dan memakai foreign key invalid

**Severity:** HIGH  
**File:**

- `apps/api/src/modules/alerts/alerts.controller.ts:14-26`
- `apps/api/src/modules/alerts/services/alert.service.ts:44-52`

```ts
const userId = req.user?.id || 'system';
```

Namun `Alert.userId` adalah required relation ke `User`, dengan ID UUID. `"system"` bukan UUID/user valid.

### Dampak

- Webhook unauthenticated dapat gagal saat insert Prisma.

- Jangan gunakan sentinel `"system"` untuk foreign key required.
- Tambahkan idempotency key dan replay protection.

## H-12 — Refresh token kemungkinan tidak pernah terbaca

**Severity:** HIGH  
**File:**

- `apps/api/src/modules/auth/auth.controller.ts:23-31`
- `apps/api/package.json`

Kode membaca:

```ts
req.cookies?.refresh_token
```

Tetapi tidak ada dependency/middleware `cookie-parser` yang dipasang. `res.cookie()` dapat mengirim cookie, tetapi `req.cookies` tidak otomatis tersedia di Express tanpa parser.

Selain itu cookie tidak memakai:

- `secure: true` di production
- `maxAge`
- `domain/path` eksplisit
- rotation/revocation

### Dampak

- Refresh flow dapat selalu mengembalikan `missing refresh`.
- Token refresh 7 hari tidak dapat dicabut.
- Risiko session replay meningkat.

### Rekomendasi

- Tambahkan cookie parser atau gunakan signed cookie middleware.
- Implement refresh-token rotation dan revocation store.
- Atur `secure`, `httpOnly`, `sameSite`, `path`, dan expiry.

# 7. Temuan Python trading bot

## P-01 — Jalur SELL menggunakan sizing dan TP/SL BUY

**Severity:** HIGH jika legacy path diaktifkan  
**File:** `trading-bot/main.py:7432-7467`

Kode hanya memeriksa limit posisi untuk BUY:

```python
if decision == "BUY":
    allowed, reason_denied = _is_position_allowed(symbol)
```

Untuk SELL:

- posisi existing tidak diverifikasi,
- quantity dihitung seperti entry BUY,
- SL tetap di bawah entry,
- TP tetap di atas entry.

### Dampak

Jika legacy execution diaktifkan:

- dapat mengirim SELL naked/oversized,
- dapat membuat TP/SL salah arah,
- risiko short/exit tidak benar.

Saat ini `_reject_legacy_execution()` memblokir order, tetapi masalah tetap harus diperbaiki sebelum runtime diaktifkan.

## P-02 — Config menyimpan credential plaintext

**File:** `trading-bot/main.py:120-135,1436-1448`

`/api/config/save` menyimpan API key/secret ke `config.json` secara langsung.

### Dampak

Credential dapat terbaca dari:

- filesystem,
- backup,
- dump,
- accidental artifact,
- akses lokal/container.

### Rekomendasi

Gunakan secret manager/KMS atau environment secret. Jika harus file, permission 0600, atomic write, encrypted-at-rest, dan jangan backup tanpa encryption.

- Endpoint dapat dipanggil dari internet karena Flask bind `0.0.0.0` (`main.py:2672-2674`).

### Rekomendasi

Terapkan auth default untuk seluruh `/api/*`, dengan allowlist eksplisit untuk health/public webhook. Gunakan `hmac.compare_digest()` untuk API key.
